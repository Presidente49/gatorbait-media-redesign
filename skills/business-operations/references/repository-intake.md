# Repository intake and native installation

This is a portable method, not an installer or substitute for upstream expertise.

1. Bind the actual client, current work item, target host and approved scope. For catalog-only reads no client secrets are needed. Inspect existing installs before adding anything; a repo mention is not evidence it was used.
2. Read the exact upstream README, license/NOTICE, skill entrypoint, plugin/MCP manifest, dependency lock and relevant installation scripts. Record source URL, commit or content hash, review date and any scope limits. Unseen instructions stay unverified.
3. Classify the component correctly. Preserve original skills/plugins intact and load their actual entrypoints and referenced instructions. A runtime needs its real dependencies, connection and smoke tests; a template stays a reference until a project requires it. A wrapper never replaces an upstream skill or creates missing tools.
4. Follow ONE documented method appropriate to the host. Keep exact upstream commands and prerequisites separate from any local adaptation. State why a change such as commit pinning is needed; never label adapted commands verbatim. Inspect remote scripts before running, honor prompts, and stop for secrets, account approvals, license issues or money. Do not execute scripts from a catalog automatically.
5. Save source, license, resolved version/checksum, install method, actual command result, host and scope in the existing work record. Installation, discovery, authentication and an actual successful workflow are separate gates. A command exit code does not prove a client task succeeded.
6. Verify in the intended fresh agent session. It must identify the original skill and version, read its required references, use the correct client profile and demonstrate a harmless permitted task. For a native plugin use its component inventory; for MCP use connection/status and tools; for a library use its actual build/test method. Never test by publishing, sending, charging or clicking ads.
7. Obtain actual next-stage acceptance for that exact artifact/version/scope. Keep failures OPEN, preserve raw errors without secrets, and use the existing cadence. No blind retries, duplicate installs or claim stealing. Roll back only the exact added component/configuration, preserving local data and unrelated hooks.
8. Record reusable findings with evidence and counterexamples in the learning contract. Keep business facts in that client. A source discovery, a mock test and a measured cross-client improvement are different outcomes.

## Access and boundaries

The catalog includes named installation adapters. They are our instructions for correctly using original projects, not repackaged upstream implementations. SOURCE_REVIEW_REQUIRED entries have no invented installation command. Full upstream copies/licenses remain in their own supported install or pinned checkout. Do not copy an entire runtime into an SKILL.md and call it installed.

Read the selected catalog row and then its original source, not the entire collection. Use user-scoped knowledge for reusable methods; use project-scoped context, connections and private memory for clients. A shared skill does not share OAuth, personal Messages, private financial records or production authority.

Do not flatten different licenses into MIT. Verify exact terms before vendoring or commercial redistribution. A free license does not eliminate compute, hosting, subscription or third-party connector costs.

## Required receipt

Record repository, resolved version/commit/checksum, host, client or knowledge-only scope, upstream method, local deviations, prerequisites, source review, command results, real discovery, authentication, actual smoke-test evidence, receiver acceptance and rollback. Status is DISCOVERED, REVIEWED, PREPARED, INSTALLED, LOADED, CONNECTED or WORKFLOW_VERIFIED only when that specific evidence exists. BLOCKED is not a successful installation. A pending source remains visible in the catalog, not silently dropped or automatically installed.
