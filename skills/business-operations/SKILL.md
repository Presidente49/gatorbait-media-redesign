# Business Operations

Use one portable method with a separate profile for each business. Keep original upstream libraries intact; load the actual relevant specialist and its required references. A saved skill is not a tool connection, installed runtime, running worker, model-training update or permission grant.

## Bind the client and work

Read the selected project's entry instructions, active controller, existing work item and explicit scope. Bind client identity before reading private data or choosing destinations. Never inherit another client's credentials, audience, brand, prices, examples or authority. No client is the global default.

Load that project's adapter or use the blank profile to identify missing essentials. Reuse existing state and incident records. Live provider evidence wins over snapshots; authorization still bounds actions. Resolve prior handoffs before starting more work.

## Load the original source

Use `commands/catalog.md` and `catalog/repos.json` to find the source-specific adapter. Read `references/repository-intake.md` for source review, native installation and access. SOURCE_REVIEW_REQUIRED means unfinished intake, not an installed dependency. For install requests, use `commands/install-repo.md`; never batch-execute the catalog.

Original MarketingSkills remains the pinned source in `sources.lock.json`, with its full skill and reference hierarchy. The existing submodule is one upstream-supported path. If a host uses the native plugin method instead, inspect and record that resolved source independently; do not pretend it matches the pin. Find the source in its actual approved checkout or native installed-plugin inventory, not by an escaping relative path from a cached plugin.

Start marketing tasks with the original `product-marketing` context skill. Then load relevant original loop, analytics, attribution, revenue, content, email, conversion or search skills and their linked references as required. The existing project specialist retains execution ownership. A library's paid-ad, connector, scheduling or outreach instructions never create local permission or a second controller.

## Run a bounded iteration

**Inspect → compare → diagnose → prepare → check → hand off → verify acceptance → record → recheck.**

Read `references/operating-contract.md`. Define an objective, baseline/time window, one success measure, source freshness, action condition, owner, smallest allowed action, verification, rollback and stopping condition. A check does not require an action. Separate real failure from stale tests, provider lag, missing access and incomplete evidence.

The producing stage retains follow-through until the actual receiving session accepts the exact project, work item, stage, artifact revision and scope. Posting a ticket or delivering a notification is not acceptance. Use `scripts/gate.py` for structural rejection of incomplete records; actual provider/thread evidence must be checked first.

The three optional native review roles in `agents/` are file-read-only specialists. They do not spawn a team automatically, dispatch production, authenticate accounts or grant permissions. The current controller can use them for bounded review without starting another orchestration system. Actual host discovery and use are separate tests.

## Learn at the right level

Read `references/learning-contract.md`. Retain observations in the client's existing record. Generalize only reviewed, supported, de-identified transferable patterns with evidence, counterexamples, a version change and a regression test. Company decisions amend that client's adapter; current metrics and IDs remain in current-state/provider records. Never promote a mock test into business lift or a single incident into universal doctrine.

## Output and finish

Return the exact deliverable/version, source/QC evidence, real owner/receiver, acceptance reference or blocker, next action and one success measure. Label prepared, installed, loaded, connected and workflow-verified separately. Keep unfinished work OPEN on the existing cadence without repetitive unchanged alerts. A terminal objective ends when independently verified or explicitly reviewed/rejected; do not invent another stage to perpetuate a loop.
