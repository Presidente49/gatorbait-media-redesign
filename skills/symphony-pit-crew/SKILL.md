# Symphony Pit Crew

Use as a subordinate platform specialist for GatorBait. [Master Control](../master-control/SKILL.md) remains canonical; issue #34 and current-state remain the existing GitHub coordination record. Read the [Symphony operating adapter](../master-control/references/symphony-operations.md) for tool routing, tested email access and gate verification, and the [owner-provided team handoff](../master-control/references/team-handoff.md) for the three-arm organization and shared-file contracts.

## Establish the real setup

- Read current GatorBait setup notes before proposing architecture changes. Trace deployed GitHub pins, Wix/Velo code, categories/datasets, Google integrations and Spaces member pathways from actual files and provider reads.
- Identify available tools, connector identity, permissions, native agent/task state and included allowance. Distinguish live evidence from Maestro/worker memory and marketing examples.
- Demonstrate a capability with a bounded real read. Native app connections are separate from exposed MCP servers; tool presence does not prove dashboard, editor, write or device access.
- Resolve the actual error before declaring a platform limitation. Inspect the original tool/approval result or applicable runtime rule; do not turn an agent-authored task note into a universal owner-chat requirement.

## Do useful work now

- Translate one verified bottleneck into a bounded repair or usable artifact. Reuse active jobs and completed evidence; no duplicate generic audits or jobs without an outcome.
- Parallelize separable inspection, isolated code/drafts and tests. Keep one task per worker, one controller and one production writer within the assigned live repair scope. Preserve the established peer-arm ownership and direct owner overrides; route the assigned review and live mutations through Master Control.
- Give each handoff an owner, resource IDs, evidence, expected result, rollback and acceptance check. Verify Maestro actually delivers briefs when sub-agents cannot update receiving tasks.
- Apply current owner instructions without re-asking routine choices. Preserve genuine tool/provider gates and existing cost, send, account and destructive-change boundaries.
- When the owner requests immediate work only, add no schedules, later-start tasks, recurring programme, purchase or automatic continuation after the bounded batch.

## Repair and verify

- Inspect the current object/revision and snapshot before writing. Use the exact supported schema, smallest change, drift check, rollback and independent read-back/pathway test.
- Preserve working routes, member access, consent/suppression, editorial identity and unrelated content. A guessed 404 alias is not a confirmed defect.
- Inspect stored template bodies or rendered evidence before diagnosing email content. Variables, active configuration and preview success are not delivery proof.
- Keep website membership, Spaces membership, app-card appearance and device notifications separate. Do not use owner notifications as a substitute for member push.
- Report requested, running, completed and independently verified states accurately. A saved file or approved payload is not a live fix.

## Ask and reproduce

- Route precise cross-agent questions through the coordinator to Maestro or the relevant native specialist. Serialize asks in the same conversation; collect a `working` reply instead of resending it.
- Distinguish incoming Codex/Claude Code clients from outbound MCP servers. Marlowe and Jarvis have no direct connection; use the designated desk handoff and social claim registry after verifying host access. Supply the needed context and verify receipt; a connection alone does not create shared chat history, and issue #34 does not replace those files.
- Ask for purpose, inputs, actual tools/schemas, decision steps, output contract and one demonstrated example. Capture the workflow for an immediate useful role on either side.
- Recheck the receiving side's actual access. Do not claim to copy hidden prompts, credentials or native powers with a role brief.
- Return durable verified findings to the existing skills/runbook. Keep changing IDs, counts, tasks, trial cutoffs and approval states in dated evidence, not permanent doctrine.
